# Design Workflow

Coordinate the smallest set of focused skills needed to ground, simplify, and
verify a digital artifact.

## Delivery

For a review-only request, report each material issue's location, evidence,
smallest fix, and verification method; leave the artifact files unchanged.

For requested edits, follow **diagnosis → change plan → authorized patch →
final verification**. Include the actual diff or changed-file paths. A proposal
is not an applied fix. Report checks actually run and their outcomes, unverified
items, and how to undo your changes while preserving unrelated work.

Verify through the intended user flow where available and state environment
limits. Bundled report validators check declarations, not product behavior.
Re-run affected checks after any later edit. Keep the delivery proportionate to
the request; a small fix does not need a full report.

## Operating principle

Use the smallest coherent visual, verbal, and behavioral system that preserves:

1. the user's primary task;
2. the artifact's verified content;
3. necessary functionality;
4. accessibility;
5. the author's or product's specific identity;
6. maintainable component and interaction contracts when reusable UI or action
   governance is in scope.

Do not infer that an artifact was generated by AI from style alone. Report
observable slop signals, not authorship.

## Required inputs

Use what the user supplied:

- artifact or source files;
- screenshot, URL, markup, component tree, or design tokens;
- design library, documentation, code, tests, or live usage when component
  behavior, interaction governance, or parity is in scope;
- intended user, primary task, and material decision contexts;
- visible, contextual, disclosed, or unavailable action paths when relevant;
- real copy, claims, dates, prices, outcomes, and constraints;
- approved product voice, terminology, nearby copy, and every locale in scope;
- target platform and release stage;
- current inventory, ownership, legacy mappings, and adoption plan when a design
  system is being introduced or migrated.

When critical evidence is absent, record it as unknown. Do not invent it.

## Choose a workflow

Select only the steps the request needs. Before the final `verify-changes`
step, combine the findings into the smallest change plan and apply the edits
the user requested. A review-only request ends with recommendations and checks
of the current artifact; it does not imply a patch. Later edits, including
pruning discovered during verification, require the affected checks to run
again before the final result is reported.

### New artifact

1. `verify-content`
2. `plan-structure`
3. `review-visuals`
4. `edit-copy`
5. `review-motion`
6. `check-accessibility`
7. `verify-changes`

Add `review-components` before the visual budget when reusable
components, action hierarchy, affordances, disclosure policy, or shared-system
adoption must be defined.

### Existing artifact audit

1. `audit-design`
2. `verify-content`
3. `edit-copy`
4. Add `review-components` when reusable components, affordance mapping,
   action priority or visibility, grouping contracts, design-system behavior,
   lifecycle, or design-code parity are in scope.
5. `review-visuals`
6. `review-motion`
7. `check-accessibility`
8. `verify-changes`
9. Re-run `audit-design` when a before/after comparison is useful.

### Design system or reusable component

1. `review-components`
2. `review-visuals`
3. `check-accessibility`
4. `verify-changes`

### Affordance, action hierarchy, or disclosure request

1. `review-components` using its interaction-governance extension
2. `check-accessibility`
3. `review-visuals` when visual treatments or grouping cues need
   consolidation
4. `verify-changes`

### Copy-only request

1. `verify-content`
2. `edit-copy`
3. `verify-changes`

### Motion-only request

1. `review-motion`
2. `check-accessibility`
3. `verify-changes`

### Radius or visual-token request

1. `review-visuals`
2. `verify-changes`

### Component contract or design-code drift request

1. `review-components`
2. `check-accessibility`
3. `verify-changes`

### Accessibility-focused simplification

1. `check-accessibility`
2. `review-visuals`
3. `verify-changes`

### Quick pass

Use for a small artifact, an early draft, or an explicit request for a fast
review without release verification.

1. Run `audit-design` once in its quick-pass mode: no category scores, no
   quality or slop-risk score, and no verdict.
2. Report up to five material changes with evidence labels and locations.
   Never pad the list; fewer findings are a valid result.
3. Apply the changes only if the user asked for edits; then recheck the affected
   content or behavior and report unavailable checks. Otherwise stop at the
   review report.
4. State which accessibility, reflow, component and interaction parity,
   design-system adoption, and reduced-motion checks were not performed, and
   offer the full workflow as the follow-up.

A quick pass must still respect the decision gates below. It may skip full
release verification and scoring; it may not skip evidence labeling, invent
support, or describe unchecked edits as verified.
Directly observed hard failures are still reported, without a release decision.

## Skill availability

This skill may be installed alone. Before each step, check what is actually
available and use the first level that applies:

1. **Invoke** — the focused skill is installed and the client can invoke it:
   activate it.
2. **Read** — the client cannot invoke it, but its package is readable at
   `../<skill-name>/SKILL.md` relative to this file's directory, not the working
   directory: read that `SKILL.md` and use its bundled references, schemas, and
   scripts from that package.
3. **Limited** — neither is possible: follow only the limited contract for that
   step in [references/composition-map.md](references/composition-map.md).

At the limited level, do not produce category scores, a quality or slop-risk
score, a verdict, or release readiness, and do not claim that a missing skill,
script, schema validator, or renderer ran. Report which steps ran at which
level, what was skipped, and how the missing skills would change the result.
Suggest installing the missing skills; do not install or download them.

## Evidence labels

Label every material statement:

- **Observed** — directly present in supplied material.
- **Measured** — produced by a deterministic check.
- **Inferred** — reasoned from evidence; state that it is an inference.
- **Unknown** — not verifiable from the supplied material.

Never convert inferred or unknown material into a factual claim.

## Decision gates

Do not issue a passing result while any of these project hard failures remain:

- fabricated customer, metric, quote, award, result, capability, or case study;
- mock or generated UI presented as proof of a real product capability;
- removal of keyboard focus, form labels, errors, text alternatives, or
  semantic structure for visual cleanliness;
- scroll hijacking without an equivalent user-controlled mode;
- essential information available only through motion, color, hover, or
  pointer-only interaction;
- nonessential interaction motion without a reduction or disable path;
- content that cannot reflow without loss at the target accessibility baseline;
- required component behavior documented in design or guidance but absent from
  the implementation or required live usage;
- a required component state or accessibility behavior that remains failed or
  unknown;
- a misleading affordance that makes inert content appear operable or maps
  materially different behavior to the same false expectation;
- a required decision context with competing primary actions and no supported
  equal-priority or no-primary reason;
- a required primary, frequent, or recovery action disclosed or unavailable
  without a supported reason and adequate path;
- a required design-system lifecycle that remains failed or unknown when
  migration or adoption is part of the release scope;
- unsupported claims presented with certainty.

A hard failure is a project release gate. It is not automatically a legal
conclusion or a complete WCAG conformance determination.

## Deliverable

Use [assets/full-report-template.md](assets/full-report-template.md).

Include:

1. scope and supplied evidence;
2. primary user, task, and decision contexts;
3. observed signals;
4. selected structure;
5. content gaps and prohibited inventions;
6. component contract, state coverage, ownership, and design-code parity when in
   scope;
7. affordance mapping, action hierarchy, visibility, grouping cues, and
   design-system lifecycle when in scope;
8. visual budget, nested-radius relationships, and justified exceptions;
9. copy decisions with locale, `correct`/`suggest`/`keep`, evidence status,
   evidence and voice basis, unresolved information, and multilingual or
   runtime parity when in scope;
10. motion decisions;
11. accessibility findings;
12. deletion plan ordered by impact and reversibility;
13. actual diff or changed-file paths when edits were requested, separated from
    proposals and deferred work;
14. verification methods, results, and the artifact version inspected;
15. unresolved unknowns and rollback instructions for applied changes.

## Completion rule

Do not optimize for emptiness or uniformity. Stop pruning when the next removal
would reduce task completion, comprehension, evidence, identity, component or
interaction behavior, action discoverability, migration safety, or
accessibility.
